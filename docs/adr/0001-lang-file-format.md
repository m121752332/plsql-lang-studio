# .lang 檔格式：256 bytes 循環 XOR ＋ 旗標描述的「筆」結構

PL/SQL Developer 的 `.lang` 沒有官方文件，也沒有官方編輯工具，所以我們自己逆向分析了格式，並且依照分析結果實作讀寫，不使用猜測式的文字處理。

**加密**：明文是 UTF-8（含 BOM）、CRLF 換行，與一組固定的 256 bytes 金鑰做循環 XOR。我們用 German.lang 做頻率分析求出金鑰，再寫死在程式裡。這組金鑰對 Languages 目錄下 14 個 `.lang` 都有效，加解密後跟原檔逐 byte 相同。

**結構**：前 12 行是檔頭（第 1 行 `:語言名稱`），之後每一「筆」以 `||` 加 30 位數字的旗標開頭。旗標每 2 位數一個欄位（共 15 個），記錄後面每一部分有幾行：

| 欄位 | 意義 |
|---|---|
| p1 | 固定 01 |
| p2 | 上層元件行數 |
| p3 | 元件名稱行數（Form 本身為 0） |
| p4 | 元件類型行數 |
| p5 | 說明註解行數 |
| p6–p8 | 英文：標題／提示／清單項目 行數 |
| p9–p11 | 翻譯：標題／提示／清單項目 行數 |
| p12–p15 | 保留（目前都是 0） |

一筆的行數 = 1（視窗名稱）+ p2 + p3 + p4 + p5 + Σp6..p15。

驗證結果：5,876 筆中 5,875 筆吻合，唯一例外是檔尾多一個空行。簡體、德文、日文、繁體四種語言共 17,628 筆的英文原文完全一致。

## Consequences

- 英文的行數（p6–p8）跟翻譯的行數（p9–p11）可以不同，例如英文 2 行、翻譯 1 行，所以不能假設英文和翻譯一行對一行。
- 修改翻譯的行數時，必須同步更新旗標裡 p9–p11 的數字，否則 PL/SQL Developer 會讀錯後面所有的筆。
